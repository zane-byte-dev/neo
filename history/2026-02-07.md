# 2026-02-07

## 工作复盘：通义千问 FaaS 压测与故障

### 背景
最近几天（2.4 - 2.7）一直处于高压工作状态，未记录日记。起因是通义千问接入我们的 FaaS 服务，需求极其紧急且量级远超预期。

### 时间线
*   **2月4日（周三）**
    *   **事件**：千问压测。FaaS 服务设计上限 500 IP，业务需求 1000+。
    *   **结果**：压挂 Redis 计数器，导致大面积 RT 超时，核心容量不可用。
    *   **决策**：建议对方切服务，但因时间紧迫，不得不硬着头皮沿用现有架构。
*   **2月5日（周四）**
    *   **行动**：紧急开发“流量透传”版本（跳过计数器，直连容器）。
    *   **进度**：开发一整天，发布至预发环境。
*   **2月6日（周五）**
    *   **故障**：原定观察后再发正式环境，但千问提前引流，导致预言的故障发生。
    *   **修复**：紧急发布透传版本。计数器问题解决，但引发新问题——Redis 存储出现超大热点 Key。
    *   **次生灾害**：
        1.  下午 3 点容器轮转，IP 数膨胀至 1500，突破 CoreDNS 上限。
        2.  Redis 版本过低，实施读写分离困难重重。
    *   **最终解决**：增加 Query Cache 覆盖热点 Case；完成 Redis 读写分离。
*   **2月7日（周六/今日）**
    *   **新问题**：
        1.  **白名单遗漏**：对方新增函数未加白名单，流量错误路由。
        2.  **缓存不一致**：昨日为解决 RDX 缓存问题调大了 TTL，导致容器轮转时 IP 更新不及时，流量打到不存在的容器。
    *   **现状**：上午修复了版本。但千问流量仍有上涨空间。
    *   **后续方案**：
        1.  为千问独立部署 FaaS 网关。
        2.  部署集成容器层。

### 痛点与反思
1.  **草台班子**：通义千问业务方对服务治理缺乏概念，两个服务之间的管理混乱。
2.  **系统边界**：团队内部对系统上限缺乏明确感知，盲目承接明星项目。
3.  **心累**：不停地在业务限制和技术债中寻找妥协方案（Workaround）。
