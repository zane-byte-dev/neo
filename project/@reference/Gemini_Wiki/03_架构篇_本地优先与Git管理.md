# 03_架构篇：本地优先与 Git 管理

## 放弃 Obsidian 的重逻辑

之前我的系统高度依赖 Obsidian 和 iCloud，但用久了发现它非常重。Obsidian 的插件生态虽然丰富，但它带来了严重的供应商锁定。当你想写个外部脚本去处理笔记时，那些特有的 ``wiki`` 语法和 `.obsidian` 配置会变成巨大的累赘。

更麻烦的是 iCloud 后台同步，时常卡顿和失效。对一个需要随时被大模型读取、被脚本调用的系统来说，文件必须是 100% 绝对纯粹的普通文本。基于这个原因，我放弃了 Obsidian 的特有语法，转投 VS Code，全部使用原生 Markdown 书写。

## 目录结构：Root-Flat 架构

不要搞无限嵌套树状层级。系统的根目录必须保持扁平且绝对清晰（Root-Flat）。
一个干脆的个人知识库，目录分层只能像这样：

*   `inbox`：一切临时想法、稍后阅读、截图。
*   `history`：按天生成的流水账和思考。
*   `project`：正在进行的代码项目或者复杂任务。
*   `source`：沉淀下来的长文、Wiki。
*   `system`：配置文件、大模型的设定、自动化脚本。

每一级目录只做它该做的事。这样的设计，大模型直接跑 `ls` 看一眼就能理解全貌。不要用五颜六色的 Emoji 标签分类，能用文件夹归类就用文件夹。

## 代码与知识的同构性

为什么要用 Git 管理笔记？因为知识和代码本质上是一回事：都是对想法的建模。

当我把所有的笔记、日记、设定和代码放在同一个大 Git 仓库下时，知识库就变成了一个真正的“软件工程项目”。你可以随时跑 `git commit -m "重构今年认知框架"`，你也可以写脚本清理过期的代码和废弃的废话笔记。知识与代码同构，才是真正的数字分身基础。
