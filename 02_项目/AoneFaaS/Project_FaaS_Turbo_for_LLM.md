# 🚀 Project: FaaS Turbo for LLM

> **定位**: 面向大模型（LLM）高并发、长连接、大流量场景的 FaaS 网关高可用架构演进与标准化专项。
> **Slogan**: 不止于修补，而是建立 AI 基础设施的新标准。

## 1. 背景与痛点 (Context)
*   **业务现状**: 通义千问（Qwen）等明星 AI 业务流量激增，原有 FaaS 架构（单函数 500 IP 上限、共享网关）难以支撑。
*   **故障频发**: 压测压挂 Redis 计数器、CoreDNS 瓶颈、热点 Key 问题、容器轮转流量丢失等。
*   **合作模式**: 业务方（草台班子）对服务治理缺乏感知，倒逼基建方被动“救火”。

## 2. 核心目标 (Objectives)
1.  **稳定性 (Stability)**: 确保通义千问等核心 AI 业务在流量洪峰下的绝对稳定。
2.  **标准化 (Standardization)**: 建立 AI 业务接入 FaaS 的标准协议（Protocol），变“被动接单”为“主动治理”。
3.  **产品化 (Productization)**: 沉淀出一套可复用的《面向大模型高并发场景的 FaaS 网关高可用架构》解决方案。

## 3. 架构演进 (Architecture Evolution)

### Phase 1: 止血与隔离 (当前阶段)
*   [ ] **独立网关集群**: 为通义千问部署物理隔离的 FaaS 网关，避免被其他业务拖累，也避免拖累其他业务。
*   [ ] **集成容器层**: 部署一层集成容器，解决单函数 IP 限制和连接数问题。
*   [ ] **Redis 治理**: 实施读写分离，增加 Query Cache，彻底解决热点 Key 问题。

### Phase 2: 立规矩 (Protocol)
*   [ ] **接入白名单**: 所有高流量 AI 函数必须提前报备并加入白名单，否则限流。
*   [ ] **压测标准**: 建立强制性的压测流程，未达标（Redis 访问量、连接数、启动时间）不准上线。
*   [ ] **容量规划协议**: 业务方需提前 N 天同步流量预估，基建方据此进行资源预热和扩容。

### Phase 3: Turbo 优化 (性能飞跃)
*   [ ] **流量透传 2.0**: 优化透传链路，降低网关损耗。
*   [ ] **大模型专属调度**: 针对 GPU 实例冷启动慢的特点，优化调度算法和预留策略。

## 4. 价值主张 (Value Proposition)
> 给老板和资本看的故事。

*   **对业务**: 提供“永不宕机”的 AI 算力底座。
*   **对团队**: 从“维修工”升级为“AI 基础设施架构师”。
*   **对公司**: 沉淀行业领先的 Serverless for AI 解决方案。
