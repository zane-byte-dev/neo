# ADR-03: 拒绝硬件过度工程，维持云端优先架构

## 1. 背景 (Context)
随着 InkBrain 系统在 Telegram 链路上的打通，以及本地笔记量级的增加，用户（Zhengchao）考虑购入一台 Mac mini 作为 24/7 在线的 AI 服务器，用于部署本地模型并作为 Telegram Bot 的宿主。

## 2. 方案对比 (Comparison)

| 维度 | Mac mini (Server 方案) | Mac Air M1 (Mobile 方案 - 当前) |
| :--- | :--- | :--- |
| **推理能力** | M2/M4 统一内存，可跑 14B-70B 本地模型 | 依赖 Gemini API (云端)，本地仅支持轻量级模型 |
| **隐私性** | 极高 (Local-First)，可实现完全断网运行 | 较高 (TLS 加密传输)，但数据经过 Google/Telegram |
| **可获得性** | 24/7 在线，手机随时调取，无感交互 | 需手动打开电脑盖子，交互是主动且间断的 |
| **成本/维护** | ~5,000 RMB + 网络环境调试 (Proxy/Tailscale) | **0 元** (利用现有设备)，无需额外维护 |

## 3. 核心决策 (Decision)
**维持现状 (Status Quo)**：继续以 Mac Air M1 为核心生产力终端，Gemini CLI 为主推理引擎。

### 决策理由：
1. **需求错位**：目前 Neo 的核心是“知识管理与决策辅助”，而非“全自动后台处理”。目前的交互频率尚未达到需要 24/7 待命的程度。
2. **重心偏差**：用户目前资产安全性高，时间价值更高。折腾硬件和复杂的内网穿透会消耗大量专注力。
3. **架构适配**：Gemini CLI 本质是云端推理，对本地硬件依赖度极低。M1 Air 的便携性赋予了“数字分身”随身移动的属性，这是固定服务器无法提供的。

## 4. 后续观察指标 (Triggers for Change)
当以下情况发生时，重新启动硬件扩容计划：
- **场景 A**：需要进行大规模异步 ETL（例如：自动将 1000+ 篇历史笔记重新打标、向量化、生成摘要）。
- **场景 B**：对数据隐私产生极端担忧，必须撤出云端 API，切换至全本地推理。
- **场景 C**：Gemini API 出现严重不可用或政策限制。
