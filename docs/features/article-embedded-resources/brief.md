# Article Embedded Resources

## Background

Neo 已经在文章编辑器里完成了一轮“编辑器优先”重构：摘要被移回正文上方，AI 改写入口从抽屉迁回编辑器更多菜单，资源能力也已经有了文章页内可达的入口。

但当前资源仍然主要停留在一个右侧浮层里。用户如果想查看这篇文章的音频概览、思维导图、报告或相关生成物，仍然需要打开 Resources Panel，在资源列表里再进入 ArtifactViewer。对用户来说，这比过去更近了一步，但仍然不是“文章内消费”。

如果文章笔记要进一步做成正文内批注，那么资源也会自然暴露出同样的问题：它们虽然和文章高度相关，却还没有成为文章阅读流的一部分。

这次需求不是要把 Resources Panel 整块塞进正文，而是重新定义资源在产品里的信息架构：

- 文章负责资源消费与轻量预览。
- 资源面板负责资源库浏览与管理。

相关来源：

- [../doc-assistant-redesign/brief.md](../doc-assistant-redesign/brief.md)：已把 Resources Panel 作为编辑器内入口引入，但仍是浮层式资源面板。
- [../article-annotations/brief.md](../article-annotations/brief.md)：已明确“笔记”要回到正文内，资源层也应遵循相同的“文章优先”原则。

## Evidence And Freshness Check

本 Brief 先核验了当前代码状态，确认资源问题不是“没有入口”，而是“入口仍以管理视角组织，而非以文章消费视角组织”。

### 1. 文章页已经有内嵌摘要，但资源仍然是 overlay

- `web/src/components/NoteEditor.tsx` 当前已经把 `summaryState` 和摘要卡片直接渲染在文章内容区域。
- 同一个组件里，资源仍然通过 `resourcesOpen` + `ResourcesPanel` 以右侧叠加浮层方式出现。

结论：当前产品已经接受“正文内摘要”这个方向，但还没有把资源也按同样原则内嵌进文章。

### 2. ResourcesPanel 仍然以“资源库”方式组织内容

- `web/src/components/notebook/ResourcesPanel.tsx` 当前结构是“内容生成 / 已生成 / 笔记”三段式。
- 它包含生成入口、Artifact 列表、笔记入口，本质上更像一个 notebook 侧资源工作台，而不是某篇文章的资源视图。

结论：当前组织方式更适合“浏览和管理资源”，不适合“贴着文章消费资源”。

### 3. 资源消费组件已经存在，但缺少文章内展示层

- `ArtifactViewer` 已经能渲染 `MindMap`、`AudioOverview` 和 `report` markdown。
- `StudioOutputs` 已经能列出所有已生成 artifact。

结论：现有问题不是没有资源内容组件，而是缺少一层“文章内轻量预览 + 跳转”的展示策略。

### 4. 当前资源入口偏 notebook 级，而不是 article 级

- `ResourcesPanel` 的生成文案明确写的是“基于所有来源”。
- 这意味着当前资源心智更接近“这个 notebook 的产物”，而不是“这篇文章的资源层”。

结论：如果要把资源集成到文章内，需要明确一套 article-level 资源表达，而不是直接照搬 notebook-level panel。

### 5. 全量资源内容不适合默认铺进正文

- `ArtifactViewer` 当前承载的是完整导图、完整音频脚本和完整报告视图。
- 这些资源体量都不小，如果默认完整嵌在长文正文里，会迅速挤压文章可读性。

结论：文章内应优先展示“资源预览与状态”，而不是所有资源本体。

## User Problem

用户在阅读文章时，和资源有关的真实需求通常是：

- 这篇文章有没有生成过导图或报告？
- 我能不能不离开文章，先快速看一眼内容？
- 哪些资源是帮助我理解当前文章的，哪些只是 notebook 里的其他产物？
- 我现在阅读到这里，最相关的资源是什么？

当前体验的问题在于：

- 资源入口仍然偏“打开面板再浏览”，会打断阅读流。
- 资源与文章主内容分离，用户需要自己在脑中建立关联。
- 所有资源都被放在同一套 panel 结构里，没有区分“当前文章相关”与“资源库管理”。
- 全量资源虽然可访问，但“先看一眼”的轻量消费路径不够自然。

## Goals

- 让用户在文章内部就能发现、预览和打开与当前文章相关的资源。
- 明确区分“文章内资源层”和“资源库层”，避免把资源管理界面直接挪进正文。
- 为音频概览、思维导图、报告等资源提供统一的文章内预览模式。
- 保留 Resources Panel 作为全量资源库和管理入口，不做一次性替换。
- 与文章内批注方向保持一致，让文章成为知识消费的主界面。

## Non-goals

- 本轮不删除现有 `ResourcesPanel`。
- 本轮不把完整 `ArtifactViewer` 默认铺在正文里。
- 本轮不先做跨文章资源推荐或复杂的个性化排序。
- 本轮不要求所有 notebook 资源都必须绑定到单篇文章。
- 本轮不把文章内资源和文章内批注强行合并成同一个面板或数据模型。

## Target Users And Scenarios

目标用户：

- 阅读长文并希望同时消费相关 AI 生成物的用户。
- 用 Neo 做研究、写作或复盘，希望文章和资源一起使用的用户。
- 已经生成过导图、报告、音频，但不想总是切换面板查看的用户。

核心场景：

1. 用户打开文章，在标题下方看到这篇文章已有摘要、音频、导图、报告等资源状态。
2. 用户在正文底部查看“本篇资源”预览区，快速浏览导图摘要或报告节选。
3. 用户点击某个资源卡片，进入完整 viewer，而不是离开文章上下文去资源列表里找。
4. 用户需要管理全部资源时，再打开 Resources Panel 浏览、重命名、重新生成或切换其他 artifact。

## Proposed Experience

### 1. 产品原则

资源集成到文章内，不等于把 ResourcesPanel 原样搬进正文。

建议采用双层信息架构：

- 文章内资源层：负责发现、预览、消费当前文章相关资源。
- 资源库层：负责查看 notebook 全量资源、管理 artifact、执行批量动作。

文章是消费场景，面板是管理场景。这两个角色不应混淆。

### 2. 哪些资源适合进文章内

建议按“与当前文章的关联强度”来决定位置：

#### A. 适合文章内展示的资源

- 摘要
- 音频概览的轻量播放器
- 思维导图的缩略预览
- 报告的摘要卡或节选卡
- 与当前文章直接绑定的批注、引用、相关来源提示

这些资源的共同点是：它们主要帮助理解当前文章，而不是帮助管理整个 notebook。

#### B. 适合继续留在资源库层的资源

- notebook 全量 artifact 列表
- 历史版本、重命名、删除、重新生成等管理动作
- 不止属于单篇文章的综合报告或跨来源资源
- 批量筛选、排序和跨文章浏览

### 3. 文章内资源布局

建议首版采用两段式布局，而不是四处散落多个 widget：

#### A. 标题下方：相关资源状态带

位置：标题和摘要区域附近。

展示目标：回答“这篇文章现在有哪些可用资源”。

建议形态：

- 若资源不存在：显示可生成入口或弱提示。
- 若资源已存在：显示小型状态 chip 或卡片，例如“音频已生成”“导图已生成”“报告 1 份”。
- 点击 chip 可打开对应资源预览或 viewer。

这一层的重点是发现，不是完整阅读。

#### B. 正文底部：本篇资源区

位置：正文结束之后、相关阅读或页面结尾之前。

展示目标：回答“这篇文章相关资源的内容预览是什么”。

建议卡片：

- 音频概览：小型播放器卡片，只展示标题、时长估计、播放按钮。
- 思维导图：展示缩略图或结构预览，点击进入全屏 viewer。
- 报告：展示标题、摘要、前几段节选，点击进入完整报告视图。

这样既保留文章主阅读流，又让资源消费紧贴文章收尾发生。

### 4. 资源的默认展开策略

文章内资源不应默认全部展开。

建议规则：

- 标题下方只显示资源状态，不显示完整内容。
- 正文底部默认显示预览卡，不显示完整 artifact 本体。
- 用户点击“展开查看”后，再进入 `ArtifactViewer` 或局部 viewer。

这样可以避免长文 + 导图 + 报告 + 音频脚本同时堆叠，导致正文失焦。

### 5. 与 ResourcesPanel 的关系

`ResourcesPanel` 不应被删除，而应转型为资源库。

转型后角色：

- 继续提供生成入口。
- 继续提供 notebook 级 artifact 列表。
- 承担重命名、重新生成、管理、跨资源浏览等能力。
- 从“主消费入口”降级为“全量浏览和管理入口”。

这会形成更清晰的心智：

- 在文章里看资源。
- 去资源面板里管资源。

### 6. 数据模型建议

当前 `Artifact` 结构更偏 notebook 级产物，若要支持文章内资源层，建议增加 article affinity 的表达。

首版可选方案：

- 为 artifact 增加 `articleId` 或 `primaryArticleId`，明确其主关联文章。
- 如果资源是基于多来源生成，可保留 `sourceIds`，同时增加“当前文章相关度”的计算字段。

目标不是要求所有资源只能属于一篇文章，而是让系统能回答“哪些资源应该展示在这篇文章里”。

### 7. MVP 路线

建议分三步推进：

#### Phase 1：文章内资源状态层

- 在标题下方增加“相关资源”状态带。
- 显示摘要、音频、导图、报告的存在状态。
- 点击进入对应 viewer。

#### Phase 2：正文底部资源预览区

- 为音频、导图、报告提供预览卡。
- 只做轻量预览，不默认展示完整内容。
- 保留“查看完整内容”入口。

#### Phase 3：资源与文章更强绑定

- 为 artifact 补 article-level 关联。
- 支持更精准地只显示当前文章相关资源。
- 评估是否需要段落级资源入口，例如“基于本段生成解释/导图节点”。

## Acceptance Criteria

- 用户在文章页内无需先打开 `ResourcesPanel`，即可发现当前文章的相关资源状态。
- 文章内至少支持一种资源的轻量预览，而不是只能跳去资源列表。
- `ResourcesPanel` 仍可继续使用，不因文章内资源层上线而失效。
- 全量资源管理能力仍保留在资源面板或 viewer 中，不强塞到正文。
- 产品信息架构上能明确区分“文章内资源消费”与“资源库管理”。

## Risks And Dependencies

- 当前 artifact 更偏 notebook 级概念，若没有 article affinity，文章内展示可能只能做粗粒度映射。
- 如果文章顶部和底部都放太多资源卡，容易再次压缩正文可读区域。
- 音频、导图、报告的预览策略不同，首版需要统一一套视觉语言，否则会显得像三套独立模块。
- 若同时推进文章内批注与文章内资源，需避免在编辑器里堆叠过多入口，导致界面重新变复杂。

## Priority

P1。它属于“编辑器优先”路线的自然延伸，不是一个额外的花哨能力。

建议优先级排序：

1. 文章内资源状态层
2. 正文底部资源预览区
3. artifact 的 article-level 绑定增强

## Open Questions

- 文章内资源层应只展示当前文章强相关资源，还是允许展示 notebook 推荐资源？
- 音频、导图、报告三类资源是否都要首版一起进入文章内，还是先从报告或音频开始？
- 文章内资源区应放在标题下方、正文底部，还是两者结合？
- `ArtifactViewer` 是否需要提供“嵌入模式”，以便文章页内复用？
- 当前摘要是否继续单独存在，还是视为文章内资源层的一部分？
