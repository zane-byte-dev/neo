# Web Voice Input

## Background

Neo 的 Web Chat 已经具备较完整的文本输入、文件上传、图片理解、文档解析和语音播放能力，但仍缺少一个面向日常对话的语音输入入口。

这使得 Web 端在移动场景、长提示词场景和口述式工作流里仍偏向“能看、能听、能打字”，但还不能自然地“直接说出来”。

相关来源：

- [ROADMAP.md](../../product/ROADMAP.md)：P1 Web UI 增强中明确列出"语音输入：Web 端支持录音并转文字（可复用语音转文字能力）"。
- [ROADMAP.md](../../product/ROADMAP.md)：P0 多模态里曾单独提到"语音转文字"，但当前仍处于未落地状态。
- [COMPETITIVE_RESEARCH.md](../../product/COMPETITIVE_RESEARCH.md)：竞品对话体验已普遍把音频作为自然输入方式之一。

## Evidence And Freshness Check

本 Brief 不是直接照搬路线图，而是先核验了当前前后端代码状态。

### 1. Web Chat 当前没有语音输入入口

- `packages/web/src/components/ChatArea.tsx` 的输入区底栏当前只有附件、项目、模型和发送相关入口，没有麦克风按钮，也没有录音状态机。
- 当前聊天输入支持文本、图片、文档上传和拖拽粘贴，但没有录音或音频文件转写流程。

### 2. 产品已有语音播放能力，但不是语音输入

- `packages/web/src/components/ChatArea.tsx` 已实现基于 Web Speech API 的文本朗读。
- `packages/web/src/components/notebook/AudioOverview.tsx` 也已实现基于 Web Speech API 的双人脚本播放。

结论：当前产品在“音频输出”层面已经有基础，但“音频输入”仍是缺口。

### 3. 后端上传链路目前不接受音频转写

- `src/routes/upload.ts` 当前只接受图片和文档，返回结果也仅有 image/document 两类。
- 现有 `parseDocument` 链路没有音频识别或转写能力。

结论：如果要支持录音转文字，不能只在前端加一个录音按钮，后端还需要新增专门的转写能力或服务抽象。

### 4. 当前代码里没有现成的语音转文字服务封装

- 搜索 `transcribe / whisper / speech recognition / media recorder` 等关键词后，未发现现成的 Web Chat 转写服务、API 路由或 provider 抽象。
- 依赖层已有 `@ai-sdk/google`、`@ai-sdk/openai`、`@ai-sdk/anthropic`、`@google/genai`，说明项目具备接入云端音频转写的依赖基础，但还没有专门封装。

### 5. 路线图里“可复用语音转文字能力”在当前代码里尚不存在

- 路线图写法暗示未来语音输入应建立在一条统一的语音转写能力之上。
- 但基于当前代码核验，这条能力还没有以服务、路由或上传链路形式存在。

结论：当前更准确的判断是“Web 端语音输入需要同时定义产品交互和底层转写能力”，而不是简单接一枚按钮。

## User Problem

当前 Web Chat 用户在以下场景下体验不顺：

- 在手机上输入长问题，打字成本高。
- 在桌面端处理灵感式、口述式问题时，文本输入打断思路。
- 需要快速把口头表达转成对话草稿时，只能依赖系统输入法或外部工具。

同时，用户即便知道 Neo 有较强的多模态能力，也会因为 UI 上没有语音入口而默认认为“Web 端只能文字输入”。

## Goals

- 在 Web Chat 输入区提供自然、低学习成本的语音输入入口。
- 用户可以录音、结束录音、等待转写，并把转写结果安全地放入输入框。
- 首版优先保证跨浏览器可用性和失败可恢复性，而不是追求复杂的实时字幕体验。
- 语音输入要复用或沉淀为一条统一的语音转写能力，而不是写死在浏览器端。
- 保持隐私预期清晰，让用户知道录音是否上传、上传给谁、是否保存。

## Non-goals

- 本轮不做实时双工语音对话，不实现边说边播、边说边回。
- 本轮不做长期保存原始音频文件作为会话附件。
- 本轮不做 Notebook 音频导入、音频摘要或 YouTube/播客完整转录工作流。
- 本轮不做桌面全局快捷键录音。
- 本轮不做连续语音唤醒词或电话式免提模式。

## Target Users And Scenarios

目标用户：

- 使用手机或平板访问 Neo Web 的用户。
- 在桌面端频繁口述需求、写作想法、待办任务的用户。
- 希望把模糊口语快速整理成可编辑文本的用户。

核心场景：

1. 用户点击输入框旁麦克风按钮开始录音。
2. 用户说完后点击停止，系统把录音转写为文本。
3. 转写结果回填到输入框，用户可继续编辑，再手动发送。
4. 如果权限被拒绝、转写失败或当前环境不支持，界面明确告诉用户下一步如何修复。

## Proposed Experience

### 1. 入口位置

在 Chat 输入区底栏新增麦克风按钮，位置与发送、附件同级，但语义上更接近“输入方式切换”，不放入附件菜单。

建议位置：

- 桌面端：输入区右侧，发送按钮左侧。
- 移动端：保持在主操作区可见，不藏入二级菜单。

### 2. 首版交互闭环

首版建议采用“录音完成后统一转写”的异步模式，而不是实时听写。

完整状态流：

- Idle：显示麦克风按钮。
- Recording：显示录音中状态、时长、停止按钮、取消按钮。
- Transcribing：显示转写中 loading，不允许重复触发。
- Review：转写文本插入输入框，用户可编辑后发送。
- Error：在输入区上方显示持久错误提示，并附修复动作。

为什么首版不做实时听写：

- 录音完成后统一转写更稳定，状态更可控。
- 更容易兼容 Safari / Chrome / Edge 的不同录音能力。
- 失败恢复更简单，便于先验证用户价值。

### 3. 默认行为

首版建议默认“转写后仅插入输入框，不自动发送”。

原因：

- 语音识别天然存在误转写，用户通常需要快速检查。
- Neo 当前对话常涉及文件、模型和工具调用，误发送风险高。
- 这和当前文本输入的心智一致，不会引入额外惊讶。

后续可考虑新增用户偏好：

- 录音结束后自动发送。
- 录音结束后只插入，不发送。

### 4. 录音态 UI 建议

录音中建议把现有输入框临时切换成轻量录音面板，而不是叠加复杂浮层。

录音态至少展示：

- 红点或脉冲指示，明确正在录音。
- 已录时长。
- 停止按钮。
- 取消按钮。
- 可选的一条简易动态条，用于让用户确认麦克风正在工作。

首版不要求真实音量波形，只要有足够的“正在采集声音”反馈即可。

### 5. 权限与失败处理

语音输入是权限敏感功能，产品必须显式处理以下失败路径：

- 浏览器不支持录音。
- 麦克风权限被拒绝。
- 当前页面非安全上下文，浏览器不允许采集。
- 没有可用转写模型或 provider。
- 音频过长、过大或格式不支持。
- 转写超时或服务失败。

错误提示必须包含修复动作，例如：

- 权限被拒绝：提示去浏览器站点设置开启麦克风权限。
- 没有可用转写服务：提示去 Models 配置支持语音转写的 provider。
- 浏览器不支持：提示改用文件上传或切换到支持环境。

### 6. 技术策略建议

建议把“录音”和“转写”明确拆成两层：

- 前端负责录音采集、时长控制、权限和状态展示。
- 后端负责统一转写服务抽象和 provider 选择。

首版推荐路线：

- 前端使用 `MediaRecorder` 录制音频 Blob。
- 新增专用转写接口，例如 `POST /api/transcribe`。
- 后端新增 `transcribeAudio()` 服务抽象，内部按已配置 provider 做转写。

不建议把浏览器 `SpeechRecognition` 作为主路径，原因是：

- 浏览器支持度不一致，Safari 和 Chromium 行为差异大。
- 难以统一质量、隐私说明和错误语义。
- 无法与 Neo 的模型配置、状态面板和故障排查体系打通。

浏览器原生语音识别可作为后续实验性 fallback，而不应作为首版核心方案。

### 7. 与现有链路的关系

语音输入不建议直接复用 `upload.ts`：

- `upload.ts` 当前语义是“把文件变成图片或文档上下文”。
- 语音输入的目标是“把短音频转成输入框文本”，不是保存文件上下文。
- 单独的 `/api/transcribe` 会更清晰，也更方便做时长限制、provider fallback 和权限错误映射。

### 8. 建议分阶段推进

Phase 1：MVP

- Chat 输入区增加麦克风按钮。
- 录音、停止、取消、转写、插入输入框。
- 支持单次短语音，默认上限例如 60 秒。
- 支持基础错误处理和权限提示。

Phase 2：增强

- 用户偏好项：自动发送 / 仅插入。
- 更清晰的权限修复说明。
- 转写语言自动识别或手动指定。
- 更好的移动端录音态表现。

Phase 3：扩展

- 浏览器原生语音识别 fallback。
- Notebook / 资料导入侧的音频转写能力复用。
- 与系统状态卡片联动，显示“语音转写服务可用/不可用”。

## Acceptance Criteria

- Chat 输入区存在可见的语音输入入口，桌面和移动端都可触达。
- 用户可以开始录音、停止录音、取消录音。
- 录音完成后，系统能够把语音转写成文本并插入输入框。
- 默认不会在转写完成后自动发送消息。
- 当麦克风权限被拒绝、浏览器不支持或转写失败时，界面能显示明确错误和下一步操作。
- 录音过程中不会破坏当前附件、项目选择或模型选择状态。
- 新增文案支持中英文 i18n，不新增硬编码中文或英文。
- 关键状态流和失败路径至少具备组件测试或 API 测试覆盖。

## Risks And Dependencies

- 浏览器录音格式在 Safari 与 Chromium 上存在差异，需要明确支持的 MIME type 和 fallback。
- 如果没有统一转写服务抽象，首版很容易被绑定到某个 provider，后续扩展成本高。
- 语音输入涉及权限和隐私预期，文案不清会引发用户不信任。
- 若转写耗时过长，用户会误以为录音失败，因此需要清晰的转写中状态。
- 若未来希望 Notebook 也复用语音转写，接口设计应避免只服务 Chat 的临时实现。

## Priority

P1。该项不阻塞核心对话功能，但能显著改善移动端和长提示词场景的输入效率，并补齐 Neo 在 Web 端“能听但不能说”的体验缺口。

## Open Questions

- 首版语音输入是否需要限制在已配置某类 provider 时才展示，还是始终展示但在触发后提示未配置？
- 录音时长上限应是多少，60 秒、90 秒还是更长？
- 是否需要把原始音频短暂保留用于重试转写，还是完全只保留转写文本？
- 首版是否允许上传已有音频文件做转写，还是只支持实时录音？
- 是否要在设置页提供“语音转写可用性”状态展示？
