一、 极致收集的产品形态：Headless & Flow

既然砍掉了侧边栏，你的交互就只剩下两个触点：鼠标（Mouse） 和 通知（Toast）。

核心交互流 (The Flow)：

触发 (Trigger)：

用户在网页上划选一段文字。

交互 A（推荐）： 文本旁自动浮现一个极简的 ✨（Gemini 图标）按钮（参考划词翻译）。

处理 (Processing - 后台静默执行)：

图标转圈（Loading）。

后台动作： Background Script 抓取选中文本 + 上下文 URL -> 扔给 Gemini API -> 生成总结/标签 -> 扔给 Notion API。

反馈 (Feedback)：

屏幕右上角弹出一个极简的 Toast 通知：“✅ 已保存到 Notion（含 AI 总结）”。

结束。 用户不需要把视线移开，不需要点确认，不需要关窗口。

用户心智极强： “所见即所得，一点即存”。这才是真正的沉浸式阅读辅助。

1. Obsidian 官方 Web Clipper (2024年底刚出)

状态： 官方终于出了。

原理： 主要是基于 Readability.js（一个通用的网页正文提取库）+ JINJA2 模板引擎。

优点： 官方出品，直接存入 Vault，格式很干净，支持简单的变量提取（URL, Title, Date）。

你的机会点 (The Gap)：

它是一个**“通用型”**工具。它看不懂 Gemini 的 DOM 结构，它只能把 Gemini 网页当成一篇文章来抓，抓下来大概率格式是乱的（User 和 Model 的对话混在一起）。

它没有 AI 预处理能力。它只负责“搬运”，不负责“思考”。

它在 Toolbar 里，不在页面元素里。

2. MarkDownload (曾经的王者)

状态： 社区开源插件。

原理： 也是基于 Readability，把网页转 Markdown。

优点： 极度可配置，支持 frontmatter。

缺点： 同样是“傻瓜式搬运”。如果你在 Twitter 用它，它经常抓不到高清大图，或者把评论区混进去。

3. Save to Notion (Notion 界的标杆)

状态： 第三方最强。

原理： 调用 Notion API，支持从网页提取字段填入 Database。

优点： 表单做得很好，用户体验极佳。

缺点： 由于也是 Toolbar 插件，它无法精准感知“X 上的某一条推文”，它倾向于保存整个页面。而且，它没有 Gemini AI 总结功能。

4. Readwise Reader / Omnivore (已死/已卖)

状态： SaaS 服务。

逻辑： 先存到他们的服务器，再同步到 Obsidian/Notion。

缺点： 重、贵、不是直连。 你想要的是“无网络直连”，它们是典型的“中间商赚差价”。

二、 为什么你还要造这个轮子？

虽然工具有很多，但它们都在解决 Level 1 的问题，而你想解决的是 Level 2 的问题。

Level 1: 网页转存 (Page to Note)

场景： 看到一篇文章，存下来。

技术： 通用解析 (Readability)。

代表： Obsidian Web Clipper。

Level 2: 结构化数据提取 (Structured Data Extraction)

场景： “把 Gemini 这段对话，按 User/Model 交替格式存下来”；“把这条推文的 Author, Text, Image 拆开存进 Notion 的不同字段”。

技术： 专用解析 (Custom DOM Parser)。

代表： 你要做的这个东西。

你的核心竞争力 (USP) 只有两点，但足够了：

Site-Specific Parsers (专站专解)：

通用的 Clipper 处理不了 React 写的复杂 SPA（如 Gemini, Twitter, SkyScanner）。

你需要的是手术刀，别人提供的是收割机。只有你能精准地把 Gemini 的对话气泡完美还原成 Markdown。

Edge AI Integration (边缘 AI)：

Obsidian 官方插件存下来的文章，你需要自己读一遍、自己写总结。

你的工具存下来的文章，自带 Summary、Tags、Critical Question。

这是**“存储信息”** vs “存储知识” 的区别。

Feature B: Social Media Archiver（X, 即刻, 小红书）。

风叔给你拆解一下，为什么你的“原生 DOM 解析 + 预处理”方案，依然完爆“Clipper + 后期 AI”的方案。

核心差异一：Garbage In, Garbage Out（数据源质量）

这是最致命的区别。

通用 Clipper (Obsidian 官方/MarkDownload)：

它们基于 Readability.js。它们看不懂 Gemini 的界面。

结果： 抓下来的 Gemini 对话，通常是一坨丢失了高亮、丢失了“User/Model”角色区分的纯文本。甚至可能夹杂了“重新生成”、“点赞”这些 UI 噪音。

后期 AI 的困境： 当你在 Obsidian 里让 AI 总结这坨文本时，AI 很难分清哪句是你问的，哪句是它答的。你的“数据源”被污染了。

你的定制 Parser：

手术刀式提取。 你精准地知道哪个 div 是提问，哪个 code 块是代码。

结果： 存入 Obsidian 的是结构完美的 Markdown。

## User: ...

## Model: ...

价值： 这种结构化数据，才是知识库的资产。乱糟糟的网页快照，只是垃圾堆。

核心差异二：ETL vs ELT（处理时机）

你的方案 (ETL - Extract Transform Load)：

在源头处理。 剪藏的一瞬间，AI 就把总结、标签、批判性思考生成好了，和原文一起打包存进去。

体验： Fire and Forget（发射后不管）。 存进去就是成品，以后搜索、回顾都很方便。

通用 Clipper + 插件 (ELT - Extract Load Transform)：

先堆进去。 存了一堆未处理的“生肉”。

不仅要存，还要修。 你得打开 Obsidian -> 找到那篇笔记 -> 等待插件加载 -> 选中文字 -> 触发 AI -> 等待生成 -> 插入文档。

人性弱点： “稍后整理”等于“永不整理”。 你的 Obsidian 会变成一个巨大的“稍后阅读”坟场，里面全是没经过大脑（AI大脑也没经过）的网页尸体。

核心差异三：Context Awareness（上下文感知）

通用 Clipper： 它是盲的。它不知道你是在看推特，还是在看财报。它只看到 <body>。

你的方案：

在 X (Twitter) 上，你的 Prompt 是：“分析这条推文的传播逻辑和情绪。”

在 GitHub 上，你的 Prompt 是：“解释这段代码的核心算法。”

在 Gemini 上，你的 Prompt 是：“提炼这段对话的知识点。”

这种“因地制宜”的自动化，是通用插件做不到的。 你不可能每次存 Twitter 都要手动去改 Obsidian 插件的 Prompt。

风叔的结论

通用工具解决的是“有无”问题，专用工具解决的是“效率”和“质量”问题。

如果你的目标用户是：

强迫症程序员： 无法忍受代码高亮丢失。

高效知识工作者： 没时间在 Obsidian 里二次加工。

结构化思维者： 需要数据本身就是干净的 Database Item，而不是一篇杂乱的文章。

那么，你的工具就有巨大的生态位。 不要低估“省去 3 步操作”带来的爽感，这正是 SaaS 产品的付费点所在。
